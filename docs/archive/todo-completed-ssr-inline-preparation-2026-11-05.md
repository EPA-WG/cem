# Shared preparation for one inline DCE — 2026-11-05

`cem_ql::ssr_preparation::prepare_inline_dce` now prepares an existing native
SSR envelope for one inline declaration and one active instance. Native HTML
import retains the exact original `Arc<HtmlDocumentAst>` and exposes the shared
CEM element tree. Downstream discovery uses typed CEM nodes and expanded names;
HTML templates remain inert and foreign declarations do not register. The
returned object retains native declaration/template/instance node identities
and the existing `RetainedTemplate` compiler owner.

This is preparation, not a completed page lifecycle. The envelope becomes
`Partial(Incomplete)` with one instance, declaration depth one and zero render
passes. It remains non-adoptable. Original page bytes, DOM owner and source maps
are unchanged. No payload is captured, island created, render plan applied,
resource acquired, script executed or output published. The renderer is used
independently in tests to verify compatibility of the retained compiled owner;
production preparation does not call it.

Source/page/base/output addresses retain their distinct meanings. Deployed
metadata comes from preflight while all authored maps keep their source URI.
Changing the physical output destination does not change preparation or compiled
semantics. Native import owns HTML decoding and the explicit CEM source handoff;
there is no parser-event traversal in the coordinator, JSON AST handoff,
HTML reparse, parallel renderer or component-profile dependency.

Decoded inline source is limited to 32 KiB. Native import's existing 16 MiB,
65,536-value and 64-depth limits remain. Preparation checks the caller's original
operation scope at entry, during discovery and around compilation/module
inspection, retaining cancellation and completed-scope codes. It does not create
a fresh deadline. The inner compiler is synchronous; complete acquisition and
execution budgeting remains coordinator work.

The first profile supports only `tag`, optional `version` and optional HTML
`xmlns` on the declaration, with one direct matching `text/cem-ml` template.
Unknown custom-element participants, customized built-in participants, ambiguous
declarations/instances, alternate templates, scoped/capability headers,
stylesheets, module maps and
external modules are refused. A direct marked data island selects resume
refusal instead of recapturing derived siblings. The strict native importer
continues to refuse script/resource-bearing source, including `<base href>`;
preflight alone cannot authorize that source. This profile does not yet preserve
arbitrary scripts as inert output or admit resource closures.

Unchanged template text retains precise original byte ranges. Entity and
line-ending transformations map conservatively to their authored run. HTML
input preprocessing occurs before character-reference decoding, so literal
CRLF/CR normalize while a carriage return introduced by `&#13;` survives.
HTML comments do not become source text. The first handoff supports
XML named and numeric character references. Other named entities and unescaped
literal ampersands are refused rather than compiled using the native decoder's
fallback spelling; author literal ampersands as `&amp;`. Broader HTML entity
support needs an extension at the shared native import boundary. Transformed
source origins survive compilation and unmapped generated bytes acquire no
invented origin frames.
Compiler/tokenizer diagnostics retain authored maps without nested-buffer
coordinates masquerading as author locations.

The original failing-first work recorded nine preparation and three import
failures before implementation. The interrupted session's temporary logs were
lost on restart, so the final validation is rerun from a clean build directory.
Additional failing-first regressions reproduced line-ending/entity and diagnostic
coordinate errors before correction. Exact results, code hashes, browser
observations and build measurements are recorded in the
[verification receipt](ssr-inline-preparation-2026-11-05.json).

Focused native preparation runs through `cem_ql:test --test=ssr_preparation`.
The explicit `cem_ql:test:ssr-preparation:stripped` target invokes Cargo with
`--no-default-features`; the ordinary executor does not forward that option.
Common import coverage uses `cem_ml:test --lib --args=import::`; existing native
renderer and declaration-artifact cohorts exercise the shared compiler changes.
`cem_ml:test:ssr-inline:browser` compares shared text vectors with Chromium while
authored JavaScript is disabled and external requests are intercepted/refused.
That comparison does not execute SSR or establish browser hydration parity.
`cem_ql:test:ssr-preparation:wasm-regression` exercises existing compiled-template
cache and retained stylesheet consumers through the rebuilt default WASM ABI.

To prevent a repeat of the disk exhaustion, this recovery run uses
`CARGO_INCREMENTAL=0`, `CARGO_PROFILE_DEV_DEBUG=0`,
`CARGO_PROFILE_TEST_DEBUG=0` and `--skip-nx-cache`, with bounded Cargo jobs.
These are verification-storage choices; default features, assertions and the
production WASM size budget are unchanged. No full-workspace validation is
claimed.

The next increment is first-connection payload capture and canonical island
preparation using the shared native island/domain owners, extracting shared
pieces where needed rather than enabling the whole experimental component
profile. Retained render-plan generation and AST application follow that.
Settling, completion proof, command lowering and browser adoption remain open.
The [proposal](../cem-ml-cli-ssr-proposal.md#611-implemented-preparation-for-one-inline-dce)
and crate READMEs describe these boundaries.

The frozen presentation bundle remains untouched. There is no public Site/UI,
CSS/theme-token or npm command ABI change and no deployment. The default core
CEM-QL WASM build is rebuilt for portability verification; npm packages and the
frozen presentation are not repackaged.
