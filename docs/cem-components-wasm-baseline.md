# Component runtime browser baseline

Reference observations from the complete current runtime, generated by
`node tools/scripts/measure-components-wasm.mjs --write-doc`. There is no
minimal profile to compare yet. Machine response/phase records and numeric memory
samples are in `dist/reports/components-wasm/browser-baseline.json`.

Core SHA-256: `b37fad5b65edd6a4510e7e9fc2751abc49a9913b40886a163b151834b4eab47a`. Chromium: 148.0.7778.96; Node: v24.16.0.

## Method and limits

- Six isolated contexts: controls, native JSON/CSV data view and a source editor
  in worker and explicitly selected fallback modes. No Studio or demo-viewer UI
  bootstrap, saved user storage or credentials participate.
- One observation per workload/mode in a shared Chromium process. Context/network
  state is fresh; process/compiled-code caches can be reused. Timings include
  automation overhead and are neither distributions nor performance comparisons.
- Readiness is visible control readiness; first use is successful form editing,
  JSON/CSV value rendering, or native CEM-ML paint with unchanged text/selection.
  Phase boundaries wait for rendering and network idle; request phases use their
  start time. Subsequent cost is already present in the full initial engine.
- This uses the assembled local demo's matched, deduplicated adapters and no-store
  server. Body size is decoded bytes; reported wire body size excludes headers.
  Body hashes come from validated served files/fixtures and response lengths so
  inspector-cache eviction does not require retaining response payloads. All
  published responses match their deployment inventory hashes and all catalog
  declaration bytes match the audited workspace. This
  does not measure compressed CDN delivery or isolated npm consumer bundling.
- Native samples describe only the selected fallback facade. Active worker and
  aggregate browser memory are unavailable through these current public hooks.
  CDP main-thread JS heap counters are recorded separately, never added to WASM
  capacity or presented as total memory.

## Observed network and first-use behavior

| Workload | Mode | Ready ms | First use ms | Cold decoded MiB | Cold unique MiB | WASM requests / unique files | First-use requests |
| --- | --- | ---: | ---: | ---: | ---: | --- | ---: |
| controls | worker | 1705 | 122 | 48.46 | 24.98 | 2 / 1 | 0 |
| data | worker | 1141 | 162 | 48.44 | 24.96 | 2 / 1 | 0 |
| editor | worker | 1637 | 183 | 48.44 | 24.96 | 2 / 1 | 0 |
| controls | fallback | 1476 | 191 | 24.97 | 24.97 | 1 / 1 | 0 |
| data | fallback | 1476 | 216 | 24.95 | 24.95 | 1 / 1 | 0 |
| editor | fallback | 1098 | 213 | 24.95 | 24.95 | 1 / 1 | 0 |

One unique binary is not one transfer or one heap. These worker observations
load the same full WASM twice under no-store delivery; fallback loads it once.
Ready/success worker counters prove that default worker jobs actually execute.
Each observed binary matches the canonical hash above. A future profile needs
separate checks for core byte size, duplicate acquisition/initialization and
optional first-use cost. No optional language/tooling WASM was loaded on first
use here: those implementations are already in the full binary.

Unavailable counters are not zero. Do not infer a memory saving, OOM threshold
or checkpoint size from these file sizes or partial heap samples. Multi-run
latency, active-worker/aggregate memory and an all-capabilities/offline total
remain follow-up baseline work in the [profile checklist](todo.md#component-application-wasm-profile-separate-target).

The fixtures add no production UI behavior or parsing. Existing component code
runs in isolated storage. Credential recovery refusal, manual recovery and the
4 MiB checkpoint/deadline contracts remain unchanged.
