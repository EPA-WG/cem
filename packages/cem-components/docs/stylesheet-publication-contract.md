# Component Stylesheet Publication Contract

**Status:** Implemented Phase 4 contract. This contract is promoted by
[`docs/todo.md`](../../../docs/todo.md), resolves the packaging stop condition
in the accepted [`action:hover` contract](./action-hover-contract.md), and is
enforced by `@epa-wg/cem-components:verify-package` plus the aggregate package
gate.

> **Migration relationship:** this is the implemented publication contract for
> the frozen legacy component stylesheet. It preserves current behavioral and
> release evidence while the inventory migrates, but it is not the CSS source
> model for a new or migrated component. The accepted replacement is embedded
> declaration CSS under the
> [CEM light-DOM CSS scope contract](../../../docs/cem-ml-uid-and-scoped-css-design.md).
> `src/styles.css` and its export shrink with legacy debt; the native `@scope`
> target does not move migrated selectors back into this file.

## Decision

`packages/cem-components/src/styles.css` is the single tracked source for the
public `@epa-wg/cem-components/styles.css` stylesheet. A package-owned,
cacheable Nx target named `build:styles` copies that source byte-for-byte to
`packages/cem-components/dist/styles.css`. The existing package-root npm
manifest exposes only the built file:

```json
{
    "exports": {
        "./styles.css": "./dist/styles.css"
    },
    "files": ["dist", "!**/*.tsbuildinfo"]
}
```

The package keeps one publication root. TypeScript, declarations, reports, and
CSS continue to be published from `dist`; there is no package-root stylesheet
copy and no `src` export. The JavaScript entry point does not import, inject, or
adopt CSS. Authors explicitly load generated theme CSS and then the component
stylesheet.

## Artifact topology

| Surface             | Exact path or identity                               | Owner                         | Contract                                                                                                                   |
| ------------------- | ---------------------------------------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Canonical source    | `packages/cem-components/src/styles.css`             | Component authors             | The only reviewed CSS source; style and browser tests consume this file.                                                   |
| Copy implementation | `packages/cem-components/scripts/copy-styles.mjs`    | Package build                 | Creates `dist` if needed and copies the source bytes to the built output. It contains no CSS generation or transformation. |
| Nx asset target     | `@epa-wg/cem-components:build:styles`                | Package project configuration | Cacheable target with exact source/script inputs and `dist/styles.css` as its only output.                                 |
| Built artifact      | `packages/cem-components/dist/styles.css`            | Nx build output               | Must be byte-identical to the canonical source and is ignored by Git with the rest of `dist`.                              |
| Public export       | `@epa-wg/cem-components/styles.css`                  | Package manifest              | Resolves only to `./dist/styles.css`; no source or package-root fallback is exposed.                                       |
| Package verifier    | `packages/cem-components/scripts/verify-package.mjs` | Package verification          | Checks topology, byte identity, JavaScript side-effect freedom, and dry-run npm contents.                                  |

The copy is deliberately mechanical. CEM theme values are already generated by
`@epa-wg/cem-theme`; component CSS only binds those public custom properties to
light-DOM component selectors. Adding Sass, PostCSS, minification, token
expansion, import bundling, or a second generated source would require a
separate build decision.

## Nx build contract

The implementation adds this explicit package target:

```json
{
    "build:styles": {
        "cache": true,
        "executor": "nx:run-commands",
        "options": {
            "command": "node scripts/copy-styles.mjs",
            "cwd": "{projectRoot}"
        },
        "inputs": ["{projectRoot}/scripts/copy-styles.mjs", "{projectRoot}/src/styles.css"],
        "outputs": ["{projectRoot}/dist/styles.css"]
    }
}
```

The package's explicit project configuration augments the inferred `build`
target with `dependsOn: ["^build", "build:styles"]`. Nx must merge that
dependency into the existing `@nx/js/typescript`-inferred target without
changing its executor, command, working directory, TypeScript inputs/outputs,
cacheability, or type-sync generator. After configuration, `yarn nx show
project @epa-wg/cem-components --json` is the executable evidence for that
merge.

`build:styles` remains separate from TypeScript compilation so each target has
truthful cache inputs and outputs. A source-only CSS change invalidates the
asset target; it does not pretend to be a TypeScript input. Running the package
`build` from a fresh checkout or after removing only `dist/styles.css` must
create the file. A cached run must restore it from the declared target output.
Repeated runs overwrite the built file with the current source and produce
identical bytes.

The copy script must fail if the source is absent, unreadable, or not a regular
file. It creates only the package `dist` directory and `dist/styles.css`; it
does not clean `dist`, traverse directories, expand globs, read environment
paths, or copy unrelated files. It may avoid rewriting an already identical
output, but that optimization must not change content or exit semantics.

## Package and release contract

The existing package-root `files` allowlist already includes all of `dist` and
excludes `*.tsbuildinfo`, so implementation adds only the exact
`"./styles.css": "./dist/styles.css"` export. It must not add `src`, a root
`styles.css`, a wildcard CSS export, a CDN alias, or a JavaScript `style` export.
No `sideEffects` field is required because the package currently does not claim
to be side-effect free; the explicit CSS import remains an author choice.

The repository's release flow already builds all projects before publishing:

- `nx.json` runs `yarn dlx nx run-many -t build` before versioning; and
- `.github/workflows/publish.yml` runs `yarn nx run-many -t build` before
  `nx release publish` with task dependencies excluded.

Making the inferred package `build` depend on `build:styles` therefore puts the
artifact on both release paths without making publication generate files. The
`nx-release-publish` target remains a publisher of already verified output and
does not gain a hidden copy step.

The implementation also adds a cacheable `verify-package` target that depends
on the package `build` and runs
`packages/cem-components/scripts/verify-package.mjs`. The aggregate package
`verify` target depends on `verify-package`. Its project configuration is:

```json
{
    "verify-package": {
        "cache": true,
        "executor": "nx:run-commands",
        "dependsOn": ["build"],
        "options": {
            "command": "node scripts/verify-package.mjs",
            "cwd": "{projectRoot}"
        },
        "inputs": [
            "{projectRoot}/scripts/verify-package.mjs",
            "{projectRoot}/package.json",
            "{projectRoot}/src/index.ts",
            "{projectRoot}/src/lib/cem-components.ts",
            {
                "dependentTasksOutputFiles": "**/*.{js,css}",
                "transitive": false
            }
        ],
        "outputs": []
    }
}
```

The verifier must:

1. assert the source and built stylesheets both exist and are byte-identical;
2. assert `package.json` maps only `./styles.css` to `./dist/styles.css`, keeps
   `dist` in `files`, and does not expose `src` or a root CSS duplicate;
3. assert source and emitted JavaScript entrypoints contain no CSS import or
   runtime stylesheet injection/adoption;
4. run `npm pack --dry-run --json` from `packages/cem-components` with a unique
   temporary npm cache outside the package; and
5. assert the dry-run file inventory contains exactly one public component
   stylesheet at `dist/styles.css`, contains neither `src/styles.css` nor a root
   `styles.css`, and excludes every `*.tsbuildinfo` file.

The verifier removes only its unique temporary cache in a `finally` path. It
does not create a tarball, contact the registry, publish, mutate the manifest,
or remove package output. Npm-pack file counts are reported as evidence but are
not pinned because normal JavaScript/declaration and report growth changes the
count.

## Author and browser-test imports

Installed-package authors use the public export after loading a CEM theme:

```js
import '@epa-wg/cem-theme/styles.css';
import '@epa-wg/cem-components/styles.css';
```

The exact theme CSS artifact remains owned by `@epa-wg/cem-theme`. Its public
`./styles.css` export resolves to the generated `dist/lib/css/cem-combined.css`
artifact and is verified through `@epa-wg/cem-theme:verify-package`.

Package-local browser specs import the canonical source with
`import '../styles.css'` from `src/lib/*.browser.spec.ts`. That exercises the
same bytes before publication while Vite owns test-only CSS loading. The
package verifier separately proves that the built/public bytes are identical,
so browser tests do not need to import ignored `dist` output or depend on a
prior local build.

Import order is normative: generated theme CSS first, component CSS second.
Neither import is added to `src/index.ts`, `src/lib/cem-components.ts`, or the
runtime installer. Server-side and JavaScript-only consumers can continue to
use the package without evaluating CSS.

## Alternatives considered

| Shape                                                                               | Decision                | Reason                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One tracked `src/styles.css`, copied by a cached target to `dist/styles.css`        | Accepted                | It preserves the package's existing `dist` publication boundary, keeps CSS reviewable, gives Nx truthful cache ownership, and avoids coupling static assets to TypeScript compilation. |
| Publish a tracked package-root `styles.css` beside `dist`                           | Rejected                | It creates a second distribution root, requires expanding `files`, and lets package-root and built artifacts drift.                                                                    |
| Export `./src/styles.css` directly                                                  | Rejected                | Source layout becomes public API, npm must publish `src`, and consumers bypass the verified build artifact.                                                                            |
| Import CSS from the JavaScript entry so a bundler emits it                          | Rejected                | It makes runtime installation styleful, excludes non-bundler/CDN consumers, and violates the explicit author-import contract.                                                          |
| Replace the inferred TypeScript build with a bundler or `@nx/js:tsc` asset executor | Rejected for this slice | The package needs one static copy, not a new compilation topology. Replacing the proven inferred build would widen risk and cache inputs unnecessarily.                                |
| Check in ignored `dist/styles.css` or generate CSS during publish                   | Rejected                | Built output must remain reproducible and untracked; publish must consume verified artifacts rather than manufacture them.                                                             |

## Executable acceptance

The publication slice is complete only when Nx proves:

- the resolved `build` target retains its inferred TypeScript command and gains
  only the `build:styles` dependency;
- `build:styles` declares only the copy script/source inputs and
  `dist/styles.css` output, and works when that output is initially absent;
- source and output are byte-identical after fresh, repeated, and cached runs;
- the package manifest exposes only `@epa-wg/cem-components/styles.css` at the
  built path and the JavaScript entries remain CSS-side-effect free;
- `verify-package` passes its topology and `npm pack --dry-run --json` checks;
- `verify-style-contract` examines the canonical source and remains green;
- the aggregate `@epa-wg/cem-components:verify` gate includes the package
  verifier and remains green; and
- the clean release-shaped package contains exactly one `dist/styles.css` and
  no source/root duplicate or `*.tsbuildinfo` artifact.

This implementation establishes a comment-only public stylesheet before the
`action:hover` fixture adds behavior. Publication did not promote a state-matrix
row or alter browser presentation. No CSS token exception was required; future
unrepresentable values must enter the
[`component CSS exception queue`](./components-css-exceptions.md) before use.

Implementation evidence:

- the resolved build retained its inferred `tsc --build tsconfig.lib.json`
  command, working directory, TypeScript inputs/outputs, cacheability, and sync
  generator, gaining only the `build:styles` dependency;
- fresh and repeated uncached copies produced identical source/output SHA-256
  `67c56130c04ca22bf46770f3914708d14d6f58c8fed11378d120cca612c43b13`;
- after removing only `dist/styles.css`, Nx restored that identical output from
  local cache without rerunning the copy command;
- `verify-package` packed 18 files with exactly one `dist/styles.css`, no
  source/root stylesheet copy, and no `*.tsbuildinfo` artifact; and
- style verification, package lint, the unchanged state audit, and the
  uncached aggregate 15-dependency gate passed all 37 tests across five files.

If adding the partial explicit `build` configuration replaces or drops any
inferred TypeScript target field, creates a target cycle, or prevents a cached
build from restoring both TypeScript and CSS outputs, stop and promote the Nx
target-composition issue as a separate decision. Do not fold CSS into the
JavaScript entry, publish a source/root fallback, or weaken the output evidence
to bypass it.
